# Research brief: game architect lens (2026-08-08)

Sourced claims gathered to ground the architect reviewer in the three-lens review of the same date. Subject-matter research, looked up at review time, not durable role-craft.

1. The @pixi/react maintainer himself advises that if you only want React to bootstrap the canvas and then work in vanilla PixiJS, you should "use pixi.js in an effect in a standard react app" rather than @pixi/react, which runs its own separate reconciler. Housewarming's split (React owns book/setup DOM, Pixi owns the room) is exactly that shape, so the review should treat @pixi/react as unnecessary weight, not a default. https://github.com/pixijs/pixi-react/discussions/611

2. In the same thread the maintainer concedes best practices are "not even totally agreed upon", that React re-renders in games "can be pure overhead", and that the working heuristic is motion in `useTick`, events in reactive state. If any Pixi-in-React layer does appear, this is the current-state guidance to judge it against, and it confirms React state must never drive the frame loop. https://github.com/pixijs/pixi-react/discussions/611

3. PixiJS v8 supports render-on-demand: `app.init({ autoStart: false })` plus manual `app.ticker.update()` / `app.render()`, and `app.stop()` / `app.start()` for pausing the shared loop. A night-resolution game only needs a live ticker while the room scene animates (candle flicker), so the architecture can stop rendering entirely while the book or setup screens are up. https://github.com/pixijs/pixijs/blob/dev/src/app/__docs__/ticker-plugin.md

4. MDN: all browser storage is best-effort and evictable by default; `navigator.storage.persist()` opts an origin into persistent mode, which Chrome and Safari grant or deny silently based on site engagement. A single-slot autosave should request persistence at first save and treat denial as a real state, not an error. https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria

5. MDN: localStorage is capped around 5 MiB per origin, string-only, throwing `QuotaExceededError` at the limit, while IndexedDB quotas are measured in gigabytes. A 30-50 night run plus playthrough log fits either, so the choice is about durability and structured storage, not size, and every write path needs the quota exception handled. https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria

6. WebKit's ITP deletes all script-writable storage, explicitly including IndexedDB and localStorage, after 7 days without user interaction with the site; home-screen-installed web apps are exempt. Since one playthrough is one sitting this mostly threatens the "come back next week to finish" case on Safari, and the save story should name that boundary rather than promise indefinite persistence. https://webkit.org/tracking-prevention/

7. MDN: in private browsing, stored data is usually deleted when the session ends and quotas may differ. The game should detect a failed or ephemeral save early and tell the player, rather than losing an hour silently. https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria

8. Standard save-versioning practice for continuously updated games: wrap the payload in a versioned envelope (`saveVersion`, schema id, timestamp), run ordered migrations on load, and keep sample saves from past versions as regression fixtures. Continuous deploys mean new code can meet an old autosave even mid-run, so the versioned slot needs migrations plus a saved-fixture test from day one. https://arcadeonstudios.co.uk/blog/a-practical-save-system-for-indie-games-versioned-portable-testable (also https://bugnet.io/blog/how-to-version-your-save-format-across-game-updates)

9. The same source warns against saving "whatever the objects contain", which drags transient runtime state into the format; save an explicit contract and recompute the rest. The already-built headless kernel is the natural owner of that contract, and the review should check nothing Pixi- or React-side ever serializes. https://arcadeonstudios.co.uk/blog/a-practical-save-system-for-indie-games-versioned-portable-testable

10. Weather Factory's launch retrospective for Cultist Simulator reports the post-launch helpdesk queue was "full of edge-case save issues and black screen crashes" despite six months of beta. Save/load and startup are the empirically dominant field-failure classes for exactly this genre, which argues for telemetry and fixtures concentrated there. https://weatherfactory.biz/after-the-dawn-what-happened-when-we-launched-cultist-simulator/

11. Kennedy also credits "a quick start", something happening in the first ten seconds, as a launch factor, saying the first couple of minutes are where you win or lose people. First contact with night one (and the known need to coach it) is a pacing question the architecture should leave room for, e.g. a scripted first night. https://weatherfactory.biz/after-the-dawn-what-happened-when-we-launched-cultist-simulator/

12. `Math.random` is implementation-defined and unseedable, while pure-rand provides seeded generators (xoroshiro128+, etc.) with a pure API where each draw returns the value plus the next generator state, and jumps for independent streams. Pure, explicit RNG state serializes straight into the save, giving reproducible spirit rolls, solver replay, and bug repros from a seed; this is the established TypeScript pattern (fast-check's own PRNG). https://github.com/dubzzz/pure-rand

13. Basic IEEE 754 arithmetic is deterministic across JS engines, but transcendental functions (Math.sin, Math.exp, etc.) are permitted to be implementation-dependent approximations. Generator and solver logic that must reproduce across browsers should stay in integers and basic ops, which trait sampling naturally does; keep floats confined to presentation. Verified via Exa grounded answer over ECMAScript-discussion sources; spec text itself not fetched.

14. Lucas Pope's own devlog says Obra Dinn's validate-in-threes exists because immediate per-fate confirmation is trivially brute-forced ("it's trivial for them to just try all the combinations and boom, game skipped"), so he priced cheating above solving. Housewarming's whole-name submission needs the same adversarial analysis: with four axes over small folklore pools, the reviewer should check what feedback a wrong submission leaks and what brute force costs in warmth. https://dukope.com/devlogs/obra-dinn/tig-30/

15. The same devlog: Pope allowed multiple synonymous correct fates because "seeing how someone dies doesn't necessarily mean you can agree on how they died". Reading a room as a scene will produce the same interpretation gaps, so trait evidence must be designed unambiguous or the naming grammar must absorb synonyms. https://dukope.com/devlogs/obra-dinn/tig-30/

16. A close analysis of Obra Dinn's confirmation system documents the endgame abuse pattern: lock two known entries and cycle the third, turning deduction into guess-and-check. The anti-spiral rule (drain shrinks per ruled-in trait) changes guessing economics, so the solver should score brute-force cost as a difficulty metric alongside deduction depth. https://intermittentmechanism.blog/2024/05/21/confirmation-in-the-return-of-obra-dinn/

17. GDC hosts "Constrain Your Content: Generating Better Content with Constraint Programming", representing established practice of generating puzzle content under solvability/difficulty constraints rather than rejection-sampling and hoping. It supports the solver-as-difficulty-instrument plan and suggests the generator and solver share constraint definitions; talk located but contents not fetched, title-level verification only. https://uat.gdcvault.com/play/1028744/Constrain-Your-Content-Generating-Better

18. In Chrome and Safari an AudioContext created outside a user gesture starts suspended and must be resumed inside a click/tap/keypress. The natural unlock is the first real interaction (starting night one); create or resume the context there, and never assume ambient audio can start on load. Verified via Exa grounded answer citing Chrome/WebKit autoplay policy docs.

19. Howler.js wraps Web Audio with HTML5 fallback, audio sprites, and cross-browser edge-case handling in a dependency-free library. A small ambient-plus-stinger set fits one sprite file, and keeping audio out of the Pixi layer keeps the kernel/presentation seam clean. https://github.com/goldfire/howler.js

20. Freesound sounds come as CC0, CC-BY, or CC-BY-NC; NC bars any commercial use without written permission, and CC-BY requires author, title, URL, and license in credits. Filter to CC0/CC-BY from the first asset and keep an attribution file in-repo, because retrofitting licenses later means re-sourcing audio. Verified via Exa grounded answer over Freesound license documentation.

21. PixiJS's official recommendation for asset organization is manifests plus bundles, with AssetPack generating the manifest from the assets folder at build time. Room-overlay art arriving per house-opening maps cleanly onto per-room or per-axis bundles with background loading, and AssetPack removes the hand-maintained manifest failure mode. https://github.com/pixijs/pixijs/blob/dev/src/assets/__docs__/manifest.md

22. Sentry's Loader lazy-loads its browser SDK and captures errors fired before full init, addressing SDK bundle weight in the play path. Given playthrough logs already flow to Upstash, the review question is whether a global error/unhandledrejection hook into that pipe suffices or a lazy Sentry earns its place for the crash classes in claim 10. https://docs.sentry.io/platforms/javascript/install/loader/

23. A Dark Room's web version is open source: a plain JS state-machine engine with localStorage saves that shipped and stayed maintained at almost exactly Housewarming's scope. It is a concrete reference for how little infrastructure a one-sitting web incremental actually needs. https://github.com/doublespeakgames/adarkroom
