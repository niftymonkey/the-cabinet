**What the record must settle, each as a craft call with evidence, or as Mark's.**

1. **The base policy's whole shape.** ADR 0053's policy moves, dodges, feeds and takes offers. Today `dodgePolicy` dodges and `nearestFood` feeds; no policy reads an offer; `belchingPolicy` spends the belch on its own rule. Decide whether the one policy also belches, because #37 story 12 and #98's third comment say no current hand can answer "one belch plus play beats the Undertaker", and a harness that never belches never reads the boss-fight belch instrument in #39. Decide it from ADR 0053 and the research's "one policy, then knobs" finding and say what it costs either way.
2. **Which of the three offer bodies the policy walks to.** The open craft call: nearest body, or the body carrying the lowest-level line, or a stated rule that combines them, with the tie-break written. It is line-agnostic either way (the fence in `lineAgnosticPolicies.test.ts` stays green by construction; say how). The take-by-slot reading #98's second comment asks for (banked offers open at the grave's own x, so a still grave is handed the middle body) is a reading the report carries, not a rule the policy carries.
3. **The two error knobs, as data.** The dexterity error (a command held stale for a drawn number of ticks) and the strategy error (a shorter look-ahead): the exact parameter each is, the three values each takes, the nine configurations and their names (a name is a plain word pair a person can say, never a number), the sharp and sloppy ends, and where the rows live. The determinism condition from ADR 0053 is binding: the stale-command draws come from their own named stream seeded off the run's seed, so one run per seed stays true; say which stream and cite how streams are named today. Precedent from the research: Talakat's two axes, Quake III's three anchors, Counter-Strike's ladder. Every value is an initial data row tuned later.
4. **The batch runner and its report.** One command runs a batch over N seeds under one configuration, headless, faster than real time, writing local tapes (step 6's store does not exist yet; say where they go and how they are named so the store can ingest them later). The report is distributions and never means: what readings it carries (the per-run readings `measure.ts` already produces, #39's instrument list, the section timeline, the stripped-rung take rate once #99 lands, the take-by-slot split, the Waking's property, reaching the Undertaker, the ending), how a distribution is printed so the tail is visible, and that every number is broken out by weapon line. Two batches compare as orderings, and a finding is believed when the sharp and sloppy configurations agree on the ordering: say how the report states that. Batch size: a recommendation with the research's reasoning (a deterministic policy needs one run per seed; cost is asymmetric across styles).
5. **The header field.** ADR 0053: one field naming which policy steered, a name string, beside `inputDevice`, and it costs a format version bump (ADR 0043) that orphans every tape before it. ADR 0053 asks that the bump be taken once, together with ADR 0056's open question of whether the director's budget travels in the header, and before ADR 0057's store starts filling. Settle from ADR 0027's rule whether the director's budget is header or build, so the bump can be taken in this step, or say exactly why it must wait and what the harness records in the meantime. What the field is named, what a human run carries in it, and how a bot run can never be mistaken for a person's.
6. **The rigs, #107.** One name per starting condition. Name the rig that starts at `SIZE_CEILING`, the one that starts at `SIZE_START` and records a tape, and the harness's own, so every figure names its rig.
7. **Verification the harness itself needs.** How the record proves the policy takes offers (runs reach levelled builds), that one seed twice is one run, that a bot tape replays and attests as a person's does, that the sharp hand reaches the Undertaker on most seeds and the sloppy hand on fewer (the done line), and that the second-carrier-killed-while-an-offer-stands corner (decision 9's condition, #98's last acceptance line) is exercised. Name the actor for each.
8. **The magnitudes section.** Every number in the record listed as an initial data row with its home, as `stage-floor.md` section 9 does.
9. **Claims in the record found false against the code.** Anything in an ADR, ticket, decision or research record that the tree contradicts, as `stage-floor.md`'s last section does. The research record already found one: `bot.ts` carries several named policies and `belchingPolicy` makes a spend decision.

**Shape.** Markdown, one line per paragraph, no hard wraps, no em dash (U+2014) anywhere, no YAML front matter. Open with the same two-paragraph header `stage-floor.md` uses (craft calls under pre-authorization item 8, every magnitude an initial data row, nothing here belongs in an ADR unless the section that says so names it). Numbered sections with plain-word titles. The record is design and evidence; it is not the dispatch plan, so no test list, no slice list, no module boundaries beyond naming the seams the plan will have to cut at.

**Do not run the test suite or any long headless batch while you work**: another agent is running `pnpm verify` on this branch and a second load reddens its suite with timeouts. A single short headless run through an existing script to check a fact is fine. Write nothing outside `apps/hungry-grave/docs/design/playing-harness.md` and your scratchpad. Never stage, never commit.

**Report in under 300 words:** the file's path and size, the craft calls taken (one line each), the items in "Needed from Mark", the glossary candidates and any ADR-level commitment you found, the record claims found false, and anything you could not close from the docs.
