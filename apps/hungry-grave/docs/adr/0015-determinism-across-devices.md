# Determinism across devices

A pinned seed replays the same run on any device, not merely in the browser that recorded it (ruled by Mark 2026-08-19). The sim advances only in fixed ticks of sixty per second: the caller accumulates real time and feeds constant deltas, the accumulator lives in the game's own code so the autopilot and the rendered screen share one implementation, its catch-up is clamped so a backgrounded tab cannot fire a burst of ticks the player has no chance to answer, and a run's length is counted in ticks rather than wall clock.

Fixed ticks alone are not enough, because they only buy determinism inside one JavaScript engine. Engines are permitted to differ in the last bit on every implementation-approximated operation, which is the specification's own term and is wider than the word transcendental suggests: it covers `sin`, `cos`, `tan`, `atan2`, `exp`, `log` and `pow`, and in practice `hypot` too, which is exactly the set a bell radius, a seeker's turn and a wisp's homing reach for. This game's testers are on a phone and a desktop by construction, which means two different engines. So the sim never calls those directly: they go through one module that rounds results to single precision, and a lint rule keeps the rest of the sim from reaching around it. `Math.random` sits under the same lint rule, since one accidental call breaks determinism outright and the seeded streams are the only source of dice. Rune runs rollback-networked multiplayer on this stack by the same method. The honest limit is that this makes divergence very unlikely rather than impossible, and it is the strongest mitigation available short of a fixed-point sim.

The way out is named here before anyone needs it: `math.ts` is where an integer-indexed sine table could later replace the trig wrappers and make that trig deterministic by construction. It is worth naming because `Math.fround` does not shrink a divergence, it changes its shape: where two engines straddle an f32 bucket midpoint, a 1-ulp f64 difference becomes a 1-ulp f32 one, roughly 2^29 times larger. The rounding is still the right first move, because it collapses the overwhelming majority of last-bit differences to nothing and costs one function call, and the table is what the escape hatch looks like if a real divergence ever shows up on the cross-device replay (named in the sim-core dispatch, 2026-08-20).

Two practices shrink the exposed surface rather than manage it. The sim prefers vector math to angle math, because a heading held as a normalized direction uses only multiply, divide and square root, all exactly specified, and needs no rounding at all. And the verification is a committed golden digest over a short scripted scenario with fixed inputs, regenerated by a documented command, because the obvious test of replaying one seed twice runs both replays in the same engine and therefore passes with a raw call still sitting in the sim: the engine is the varying input, and a same-engine test is structurally blind to it. The scenario stays short and tuning-stable, or the final tuning dispatch reddens it on every retune.

The reason this is worth a module and a lint rule rather than a scoped-down promise is that divergence compounds through the economy. Spawns would survive a sloppy version, because rows fire off the stage clock. Drops would not: they are priced in kills (Hungry Grave ADR 0002), so one bent projectile path kills a mob half a tick later, the kill count crosses a drop price at a different moment, and within about a minute the two runs are different builds with different weapon lines. A pinned run that is only mostly identical is not mostly useful. Hungry Grave ADR 0012 makes the pinned run both the playtest instrument and the shareable challenge, and both of those need the same run, not a similar one.
