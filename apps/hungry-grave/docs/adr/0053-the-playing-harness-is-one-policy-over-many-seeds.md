# The playing harness is one policy over many seeds

The machine that plays the game is one policy run over many seeds, and only then the same policy wearing two error knobs. The policy moves, dodges, feeds and takes offers. The knobs are a hand and a head: a dexterity error that holds a command stale for a drawn number of ticks, and a strategy error that shortens how far ahead the policy looks, each at a few values, which gives a small set of named configurations from a sharp hand to a sloppy one. A roster of named personas over a weight vector is not built, because the authors of every shipped persona roster say the same thing about hand-set weights, that they are guesses until there is play to point them at, and the play this project will point them at is friends' tapes ([../research/playing-harness-precedent.md](../research/playing-harness-precedent.md)).

What the harness produces is comparisons and never thresholds. Four studios found independently that relative difficulty is invariant to the policy: EA on two titles, Tactile, and Ubisoft, whose agent sat far under its humans in absolute terms and still moved the same direction per player cluster. That is what makes a weak bot worth running, and it is also the constraint on how its numbers may be read: this build against that build, this configuration against that one, never this number against a target. A batch reports a distribution rather than a mean, because the interesting runs are in a tail, and a finding is believed when the sharp and the sloppy configurations agree on the ordering.

The harness measures and never judges. Whether the game is fun is a person's answer, ADR 0013's ruling, and the automated player measures its own policy rather than the game. Cave's own automated instrument, an invincible run used to bound the score, under-read its humans by a third, which is the shape of the mistake available here.

Three properties travel with the decision. The offer goes into the dodge policy before any second style exists, because until the bot can take a drop no two styles have anything to differ about, and since an offer is taken by passing under a body, the take is a movement target and needs no new command channel, only a rule for which of the three to walk to. A deterministic policy needs exactly one run per seed, so batch size is seeds and never repeats, which holds for the sloppy configurations only if the hand's stale-command draws and the head's shortened look-ahead come from their own named stream seeded off the run's seed. Drawn any other way, two runs of one seed differ and one run per seed is false. And replay is untouched, because a tape records the commands the simulation consumed, whatever produced them.

The header gains one field naming which policy steered, beside the existing input device, so a bot run is never mistaken for a person's, and that field costs a format version. The header is positional, read field after field in a fixed order (`src/tape/records.ts`), so adding one changes the wire grammar and moves ADR 0043's format version, which stops every tape recorded before the bump from decoding. The policy is recorded as a name string and never as a code byte, because the set of policies is open and a positional or ordinal encoding over an open set is the exact mistake ADR 0043 was written against. The bump is taken once rather than twice: together with ADR 0056's open question of whether the director's budget travels in the header, and before ADR 0057's store starts filling, because after that a bump orphans rows in a database as well as loose files.

Which of the three offer bodies the base policy walks to is left open, and the per-line preference belongs to the roster if the roster is ever built.
