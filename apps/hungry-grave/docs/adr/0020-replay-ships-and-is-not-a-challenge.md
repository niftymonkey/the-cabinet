# Replay ships and is not a challenge

Replay is a committed player-facing feature and not only a tuning instrument. Mark committed it to the final product outright in the analytics and replay grill: share a good run and a friend watches it like they were over your shoulder. It stays inside the v1 done-line, and the reason it does is not sentiment, since the instrument half is upstream of the tuning that #36's one open criterion and both bosses need. The player-facing half, where a player saves a tape they can keep and opens one somebody sent them, has its own ticket in #49 rather than being assumed: getting a tape out of a browser and back into one belonged to neither dispatch, with no ticket, no trigger and no owner, and the v1 box line is trimmed to what the dispatches actually deliver.

**A challenge and a replay are different features and neither substitutes for the other.** Sharing a seed gives somebody the same dice and their own hands; sharing a tape gives them the run that actually happened, watched rather than played. Folding the two together under one glossary term is what once forced the word "replay" onto an avoid-list, and that fold no longer holds. Hungry Grave ADR 0012 keeps the pinned seed as the challenge and as the playtest instrument, and this is the other half rather than a variation on it. The stage is authored and a seed varies only columns, drop kind and fire jitter, so a shared seed is a much smaller thing than it sounds.

**The shipped player route is reserved now and deliberately not built.** The reserved shape is `#/watch`, which names the player-facing watch screen and leaves the tape source unresolved, so a file picker and a stored id can both land inside it later. Reserving `#/watch/<id>` instead would presuppose an id space, which is exactly what a local file does not have, and would reserve only the deferred half of sharing. `#/replay?tape=<url>&at=<tick>` is the instrument route, for the agent and for development, and it stays that: a player-facing feature must not later be built on a debug URL. Sharing a tape over a link is deferred past v1 with an observable trigger, the first time a run has to reach somebody who cannot be handed a file, because #26's own rule is that an item which cannot name a trigger is cut or graduates on the spot and a blob store is a dependency rather than an event.

**The observation layer this rests on serves an open pool of purposes, and the tape is one artifact for all of them.** Gameplay and tuning evidence is one purpose and performance evidence is another, first-class beside it rather than a sidecar to it, and Hungry Grave ADR 0018 carries the format and the rule that splits them. What belongs here is the consequence for the seams: they are shaped for observation in general and never for the recorder in particular, because the recorder is one consumer and the pool is open by design in the same way weapon lines and mob types are (Hungry Grave ADRs 0005 and 0016).

**There is a frame-level observation seam alongside the per-tick one, and it is architecture rather than a ticket detail.** `TickListener` fires inside `executeTick`, once per tick, so a tick hook can only ever see the simulation. Frame interval, FPS, ticks executed in a rendered frame, and the announce and sync costs are all frame-level, and they live in `GameScreen.update`, which today calls `advance`, `announce`, `syncScreen`, `syncReadouts` and `endedIn` inline with nothing observing any of it. That is the seam most likely to be wanted by a use nobody has named yet, for the same reason the tick hook cannot serve it. What the seam has to produce is fixed by Hungry Grave ADR 0018's requirement rather than by any one consumer of it: frame observations reach a structured run record an agent can analyse, and never a number a person reads off the screen and types back. A readout in the corner of a screen is a fine thing for a human watching a run happen and it is not evidence, because it carries nothing that joins it to the run it came from and it is gone with the frame that drew it. The seam lands with the deterministic core rather than after it, and the deciding reason is Hungry Grave ADR 0018's split rather than any convenience of the code (ruled by Mark 2026-08-23): frame cadence, ticks executed per frame, debt growth and the runtime and renderer context are measured evidence, so a run that did not capture them has lost them for good, while every gameplay fact beside them is recoverable from the tape whenever somebody thinks to ask. What lands with it is the minimum and is named to stay minimum: the seam, the per-frame evidence row, the per-run runtime and renderer header, and the format support for carrying them. Storage policy, readers and analysis, any interface, richer entity and load measurement, sub-tick timing and RxJS are all outside it.

**Two more things land with it, and both are scaffolding rather than features** (ruled by Mark 2026-08-23). The dispatch has to be able to prove its own claims rather than depending on future infrastructure to say whether always-on checking was safe, and it cannot do that if the evidence it records dies with the tab on the one device the question is about. So it takes **a minimal export**, the smallest plumbing that retrieves a recorded run from a phone, which the research settles as an `<a download>` on a `blob:` URL fired from inside a real tap handler, supported on iOS Safari 13 and later. And it takes **a development-only way to pin the weapon loadout**, because the measurement's stated condition is a dense moment with the lines levelled and no reachable run produces that: going from the birthright to level five on all four lines costs eighteen drops and the stage's drop table pays for at most twelve.

**Naming what each one is not matters more than naming what it is.** The export is temporary plumbing and never the storage or analytics system; a later system may send this evidence straight to durable storage, at which point the manual escape hatch stops being necessary and is removed rather than grown. The loadout pin is a development and testing control and never a player-facing feature; it exists so a measurement is reproducible, not so a run can be started rich. Both are built at the smallest size that yields a trustworthy apples-to-apples reading, and the standing constraint in Hungry Grave ADR 0018 is what judges "smallest".

**RxJS is an intentional future candidate for app-level observation and composition, to be taken up when those consumers justify it. It is not a rejection and nothing here is designed away from it.** It was not evaluated and found wanting: it was found to have exactly one consumer at the moment the question was asked, the tape recorder, because `src/dev` carries `mayImport: []` and the instruments, by far the largest set of observers being built, can never import it. Adding a dependency for one consumer is the thing Mark ruled out, in his words, because he did not want a use case manufactured before one existed. The line he drew instead is the standing one: the ticker for continuous simulation, direct calls for authoritative state changes, and RxJS for observation, coordination and derived behaviour across systems, with the deterministic simulation itself never depending on it.

Where it earns its place is derived behaviour the synchronous path cannot express at all: throttling repeated hit sounds, debouncing a stutter, combining two streams to say "belched while at the size floor". **Composing frame, execution, gameplay-load and runtime observations over time is exactly that shape, and performance observation is now a second concrete app-level consumer rather than a hypothetical one.** Mark named that composition on 2026-08-23: the record Hungry Grave ADR 0018 requires is built from those four kinds of observation joined over time, and the join is derived across streams rather than read off any one of them. Naming a consumer is not scheduling one, and the candidacy is exactly as stated above, taken up when the consumers justify it. The seam is already shaped to accept it and the adapter is about ten lines. `executeTick`'s synchronous listener hook is a real seam by the two-adapter rule rather than indirection for its own sake, with an RxJS adapter in `src/app` on one side and a plain direct listener in `src/dev` that must be able to throw on the other, and Hungry Grave ADR 0017 records why the authority itself stays dependency-free and synchronous.

The rule about `RunState` crossing into an observation layer is stated as the hazard and not as a wall, because Mark corrected the first version of it. A live mutable `RunState` reference must never be retained, buffered, replayed or otherwise treated as a historical value, since `events.ts` already warns that payloads carry values and never entity references because the pools are mutated in place, and "never retain state" is a discipline rule rather than a machine one. Projecting state into safe value snapshots at the adapter is the mechanism that prevents it; it is not the principle, and RxJS is not the boundary that cannot be crossed.

Converting `sound.ts` and the renderers onto a stream is a dont-build, and it is not what the candidacy above invites. Their existing frame-batched `SimEvent[]` path is intentionally well-suited to raw dispatch, and a swap would cost three guarantees for nothing. Delivery becomes per tick rather than per frame, so `erupt` would see the state at the belch tick rather than the state at the end of the frame, which is a behaviour change to Hungry Grave ADR 0014's announcement channel that has to be decided on its merits and never inherited from a plumbing change. Failure isolation inverts, since an error reaching a subscriber terminates that subscription permanently, so one throw kills sound for the rest of the run silently, against a `try`/`catch` whose own comment says sound is the one subsystem whose failure must never take the run with it. And lifecycle stops being free, on screens that are pooled and where a missed unsubscribe leaks a live subscription per run that keeps receiving. `sound.ts` is also the only file in `src/app` with its own row in `src/boundary.test.ts`, so putting a dependency in it means widening the one allowlist the design deliberately fenced.

Ruled by Mark in the analytics and replay grill on 2026-08-22 and on #48 and #45 on 2026-08-23, where he asked in terms that this be recorded as an intentional future candidate and never as a rejection.
