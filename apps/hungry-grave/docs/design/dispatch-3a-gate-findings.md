# Dispatch 3a gate findings and dispositions

All three gates ran at standard depth on 2026-08-20 against `dispatch-3a-sim-core.md`. Markers are on #36: product vision `5361754391`, game design `5361767886`, tech architecture (posted, same thread).

**None of this is folded into the plan yet.** This file is the fold-in list. Work down it, edit the plan, then delete this file in the same commit that lands the revised plan.

## Closed by the record: fold in without asking

**The score rung bleeds all of it.** Section 4.6 says "bleed it and stop" and four paragraphs later calls the amount tuning. Two ladders from one section, and a coding agent picks one. Only "all of it" makes the score tier exactly one rung, which is what test 37's finiteness bound needs: a proportional bleed is Zeno-infinite and a fixed amount makes the bound depend on a magnitude the test is forbidden to know. My own test list already argued for this. Sonic is the precedent and it is on this side: later games' partial ring loss *reduced* tension because a large total trivialised risk.

**Every landed hit starts invulnerability, including a floor hit that does not shrink.** Both product vision and tech architecture caught this independently and it is the plan's worst bug. Section 4.6's whole WCAG argument rests on the invulnerability window being the dim's refractory interval, and the plan only ever says a hit starts it in the shrink case. Test 36's "bleeds score and nothing else", written twice, reads as forbidding the invulnerability write. If floor hits skip it the ladder runs in consecutive ticks: sixty dims a second, a flat SC 2.3.1 failure, in the one state where the player is a hit from sealed shut. Reword test 36 so "nothing else" constrains which rung runs, not what else the hit does. Test 37 has to age past the window between rungs.

**Test 23 needs `>`, not `>=`.** At 20 ticks hits land at ticks 0, 20, 40, 60, and 0 through 60 is one second, so four flashes. SC 2.3.1 forbids "more than three times in any one second period", so the period must exceed a third of a second: 21 ticks at 60 Hz. The general rule is worst case `floor(1/p) + 1`.

**Quote the full SC 2.3.1 conjunction in the code comment.** The plan says "the ten percent relative luminance threshold" and drops the second half: a general flash needs a pair of opposing changes of 10% or more *and* the darker image below 0.80 relative luminance. Trivially satisfied on this palette, but the abbreviated form is exactly the citation shape this project has been burned on twice. Also worth knowing: the area escape hatch cannot apply to a full-field dim, and SC 2.3.1 invokes Conformance Requirement 5 Non-Interference, so unlike 2.3.3 there is no "essential to functionality" carve-out. A game gets no exception.

**Drop mulberry32 for sfc32 seeded through xmur3.** This is the finding to read twice. mulberry32's state update is a fixed additive Weyl step over an odd constant, so every instance walks the *same* single 2^32 cycle and the seed only picks an entry point: the four named streams are four windows into one sequence, disjoint by arithmetic luck (smallest pairwise gap about 2.2e8 draws against a run's ~1e4) rather than by construction. Slay the Spire 2 shipped exactly the seed-plus-name-hash fix in section 4.2 and correlated anyway, with real consequences (a card mathematically unobtainable, potion drop rates swinging 76% to 4% by act). mulberry32's author withdrew his own recommendation in 2022: not equidistributed, cannot produce about a third of all uint32 values, fails PractRand at 32GB. FNV-1a fails SMHasher avalanche outright, and on the actual stream names differs in 7 of 32 bits against an expected 16. sfc32 is integer-only over the same exactly-specified operations, so the engine-stability argument is fully preserved, has 128 bits of state so overlap stops being a number anyone computes, and PractRand lists it as recommended. Not a bigger module. Do NOT reach for PCG: O'Neill concedes its streams are not statistically independent.

**Pin the fold operation to addition, not XOR.** With addition the pairwise offsets are the same for every seed and a test can verify them once. With XOR they vary per seed, the property becomes unverifiable, and a bad pairing is a heisenbug on exactly one shared challenge URL.

**Rewrite test 9.** It compares sequences from draw 0, so it passes even when two streams are offset by three draws, which is the actual failure mode. Assert instead that the minimum pairwise offset exceeds a run's whole draw budget by a wide margin. That also fails loudly the day a fifth stream name is added. This survives whatever generator is chosen.

**Restrict all 22 of ECMA-262's implementation-approximated functions in the lint rule, wrap only the ones used.** The plan names 8 and leaves `atan`, `asin`, `acos`, `cbrt`, `log2`, `log10`, the hyperbolics and the rest open. `asin`, `acos` and one-argument `atan` are exactly what dispatch 4's seeker turn and dispatch 5's wisp homing reach for. The prior tech gate's finding on the tracer plan was "widen to the whole set" and narrowing to 8 partially drops it. Blocking a name with no wrapper yet is a feature: it forces the conversation when someone needs it.

**Drop `hypot` from math.ts.** `Math.sqrt` is exactly specified as of tc39/ecma262 PR #3345 (merged 2024-08-17), so `Math.sqrt(x*x + y*y)` is fully deterministic while `Math.hypot` is not. In a 540 by 760 field there is no overflow range to protect. `normalize` already returns the length.

**`x ** y` really is `Math.pow`** (both are `Number::exponentiate`), and V8 shipped a real divergence between the two spellings, v8 issue 5848. Keep the operator rule and cite the bug, not just the spec.

**Clamp elapsed time on the way IN, not the tick count on the way out.** Gaffer clamps `frameTime` before it enters the accumulator so the dropped time never accumulates. Section 4.3 clamps the returned count and leaves the accumulator holding time it refused to spend: a 5000 ms frame leaves about 4750 ms behind and every later frame clamps at 15 forever, which is the spiral of death arrived at *through* the clamp. Tests 15 and 16 both pass on a fully saturated accumulator. Clamping `elapsedMs` to `MAX_CATCHUP_TICKS * TICK_MS` on entry makes the drain structural and the bug unwritable. Add the test either way: after a clamp, a normal frame yields a normal tick count.

**`clock.ts` takes raw elapsed, never Pixi's `deltaMS`, and needs a visibility-reset seam.** Read from installed pixi.js 8.19.0 `Ticker.mjs`: `_maxElapsedMS` is 100 and the clamp applies to `deltaMS` only, after `elapsedMS` is assigned the raw value. Feed `deltaMS` and the 15-tick clamp is unreachable, `debtTicks` reads zero forever, and any `speed` change silently rescales the sim. Feed `elapsedMS` and a tab switch dumps its whole gap into the debt counter, so one backgrounding reads as a struggling phone. Pixi ships no `visibilitychange` handling. Phaser's answer is a `panicMax` cooldown after a tab switch. Without the seam, either the debt readout or the clamp is a lie. State the contract in 3a even though the consumer is 3b.

**`pnpm test -- -u` does not work.** Verified in this repo: pnpm 10 forwards the bare `--` through and vitest routes everything past it into a bucket it never reads, so it runs the suite, updates nothing and exits zero. `pnpm test --zzbogus` errors; `pnpm test -- --zzbogus` passes silently. The working form is `pnpm test -u`.

**Replace the vitest snapshot with a committed constant plus a print script.** `-u` maps to update mode `all` and rewrites every changed snapshot in the run, so an unrelated `-u` for a future renderer snapshot silently rewrites the determinism digest. `CI=true` does not save it: a truthy `update` skips the CI branch entirely. `toMatchFileSnapshot` is writable by `--update` too. The plan's only defense is a prose warning, which is the "comment asking nicely" section 4.10 rejects one page earlier for the lint rule, and the argument applies with the same force. Use the Go golden-file shape: a plain constant compared with `toEqual`, plus a script that prints the regenerated value for a human to paste. Keep the readable object form, not a hash: an object diff names the field that diverged.

**Two digest blindness notes for the test file.** Nothing on 3a's digest path calls `math.ts` at all, since the grave moves linearly and the scroll is linear, so a green digest in 3a is not determinism verified and later dispatches must extend the scenario. And `moveGrave` clamps to the field edges, so a script holding full-right pins `x` to the wall exactly and erases divergence in it: keep the script off the walls, and consider an accumulating per-tick checksum so a divergence that later re-converges still shows.

**One declaration of the field constants, in `src/game`, imported by `src/app/layout.ts`.** The boundary does not forbid this: `BOUNDARIES` governs `game`, `input` and `dev` only, `src/app` is ungoverned, and `GameScreen.ts` and `runHandoff.ts` already import from `src/game`. ADR 0003 settles ownership: the sim runs in the fixed field and the renderer scales it. Put them in `src/game/field.ts` rather than `tuning.ts`, since these two are ADR 0003 and not tunable. Test 25 disappears rather than being written.

**Declare `SCROLL_SPEED`, derive `FRESHNESS_SECONDS` from it.** The plan has the causality backwards. ADR 0004 and the concept doc both state it: "the seconds are derived from scroll speed... so a scroll-speed retune retunes the meter with it." The invariant is symmetric so test 20 is unaffected, but the ergonomics are not. Scroll speed is the reaction-time budget for every threat on the field and sets how long a mob is on screen; freshness is one deadline on one food class. Under the plan's direction, making the game feel faster means editing a constant ADR 0004 pins at "about ten seconds". That is a trap laid for a future self.

**Start `INVULNERABLE_TICKS` near 24, not 60.** Convention is 0.2 to 0.4 seconds, set so the window stops multiple hits from one attack rather than letting a player tank a curtain (Brotato, Hollow Knight). 60 ticks is 2.5x to 5x that and 3x its own WCAG floor. At one second, deliberately eating a hit to cross a wall is probably the dominant play, which collides with decision-log entry 12: the Wall must be crossable unloaded but never crossable for free. It also spaces the floor ladder's rungs at a second minimum, which is what turns the strip tail into a thirteen-second one. 24 ticks is 0.4s, the top of convention and above the corrected WCAG floor of 21. Say in the plan that the 60 was not load-bearing for the accessibility argument.

**Derive `MAX_CATCHUP_TICKS` as `Math.round(250 / TICK_MS)`.** Everything else in `tuning.ts` is derived and section 4.4 argues at length for why. Note `Math.floor` gives 14, since 250 / 16.667 is 14.99999. Cite Gaffer as a safety valve rather than a derived figure: it is arbitrary in the source, introduced with no stated reason, and peers disagree freely (Unity 0.3333, Pixi 0.1, Godot caps steps instead).

**Entropy stays in `run.ts` with a narrow documented lint exception.** ADR 0012 and `run.ts`'s own JSDoc both put the roll in the sim so a run's identity is the sim's. Document it beside `clock.ts`'s "not deterministic and does not need to be" carve-out rather than moving the roll to `src/app`.

**`moveGrave` applies the command as given and does not normalize.** ADR 0011 puts normalization and the cap in each input model and makes touch deliberately uncapped, recording that capping touch to keyboard feel WAS the input lag felt on device. Test 28's diagonal cap inside `moveGrave` contradicts that. Move the diagonal assertion to `keys.ts` in 3b.

**Name `belch.ts` in section 4.7.** Tracer plan section 3 gives `belch.ts` "reservoir fill per swallow, the cap, the visible splash past full" and the plan puts all three in `swallow.ts` without mentioning it. Both product vision and tech architecture flagged it. Keep the charge in `swallow.ts` since the swallow is what charges it, and say `belch.ts` takes the firing and the eruption, so dispatch 5 is purely additive.

**Add feast tests.** `FoodKind` includes `"feast"` and section 5's fifteen swallow tests never mention it. It is the only food that can cross the ceiling and the reservoir cap in the same swallow, and the ordering (`reservoirFull` before or after `splashed`, ceiling overflow compounding with maxed-line overflow) is fully specifiable on plain values now. Dispatch 6 is where the Banshee beat lands and by then the arithmetic is frozen.

**`RESERVOIR_CAPACITY` 100 is unreachable and must be derived.** It is the plan's one underived number in a file where everything else carries its reason. Decision-log entry 5.11 and the concept doc both pin the coupling: the Banshee's feast pays growth worth 8 to 10 fresh trash corpses AND slams the reservoir full. Under one shared payout number, 100 against a `SIZE_CEILING` of 67.5 means a full reservoir costs more cumulative growth than the entire floor-to-ceiling range, so the run's most choreographed beat is arithmetically impossible and no test notices. Either derive capacity from the feast payout in the `SCROLL_SPEED` idiom, or unweld growth from charge, since no ADR says they move together (ADR 0004 governs the multiplier, not the base).

**Live streams belong in `RunState`, and `Stream` should expose its cursor.** Section 4.8's list of what `run.ts` gains omits them. Nothing in 3a draws so the dispatch completes without answering it, but the seam is pinned here: without the cursor in the digest, a divergence in *how many* draws a tick made is invisible to the one test built to catch divergence, and 3b's `?seed=` replay cannot resume mid-run.

**`hitGrave` is the single entry point for all damage.** State it, so dispatch 4's mob contact damage (ADR 0016) routes through it rather than shrinking the grave itself.

**Scroll distance is redundant state.** It is `tick * SCROLL_SPEED` exactly. Derive it: one less field in the digest and one less thing that can drift.

**`grave.ts` needs `import type` for `RunState`**, or `run.ts` importing `createGrave` at runtime closes a real cycle rather than a type-level one.

**Test 58 needs a small refactor named in the plan.** `violationsIn` takes a path and reads from disk, so there is nothing to hand it for the "a non-test file importing src/dev is still a violation" case. It needs a pure inner function taking source text and a display path, with `violationsIn` reading and delegating. Otherwise this turns into a fixture file nobody expected.

**Three record edits.** Tracer plan verification step 3 still says flatly "Nothing under `src/game` imports `src/dev`", which after the 4.9 change disagrees with the boundary test and needs the test-file qualification. ADR 0014 still reads "the dim needs a stated refractory interval" as open after this plan closes it, so it gets re-argued: close it there and add that at the size floor a hit does not shrink, so the rim channel is silent and the ladder events (`scoreBled`, `weaponStripped`, `sealed`) are the only second channel left. And rename `lines/lines.ts` to `lines/roster.ts`, which stops stuttering beside `soulStream.ts` and the rest.

**Two nits with no consequence.** The `SIZE_FLOOR` rationale says the resize plugin "upscales a 390-wide phone window to a 540-wide stage" when it scales the field down to 0.72 CSS pixels per unit, which is the number `layout.ts` already documents and supports the same conclusion. And `Rect` is declared in `grave.ts` while `overlap.ts` arrives in dispatch 4 wanting to own it.

## Confirmed good, do not churn

Testing derivations rather than magnitudes: product vision called it the strongest thing in the document and game design agreed and would keep it exactly as written. Specifying `swallow` on plain values a dispatch before its callers: the best structural move in the plan. The 4.9 boundary change: narrow, guarded by test 58, consistent with the file's own existing `packagesAllowedIn` test-file widening, and `invariants.ts` should NOT move into `src/game`. `lines/roster.ts` pulled forward: the ladder cannot be written without knowing which lines exist and which two are the birthright. "Size never gates a swallow" survives cleanly and every path that could smuggle a gate in is closed the right way. The vocabulary is clean. `GRAVE_ASPECT` 2 is better sourced than the plan claims: a standard adult grave space is 42 by 96 inches, 2.29:1, so 2 is an actual plot dimension. `architect-deep` does NOT need re-firing.

## Ruled by Mark, 2026-08-20, after the gates reported

**The floor's weapon rung takes one level off EVERY line per hit, not one level from one line.** The ladder is bounded at five rungs whatever the build, because MAX_LEVEL is 5, so a great run and a poor one die at the same length. Each rung visibly thins the whole storm in one beat rather than drizzling a level away. ADR 0003's ordering is untouched: score first, then weapon levels down to birthright, then sealed shut. Test 37's bound gets much tighter. What this replaces: one-level-per-hit gave about 11 strip rungs on a 10-to-12-drop run, roughly thirteen seconds of low-agency dismantling that got longer the better the player had done, which is the slow-motion execution the shmup literature names.

**The bled score does NOT scatter as swallowable scraps, and this is parked rather than refused.** Trigger to revisit: the #31 playtest's spiral-versus-comeback read. The question the scraps answer is whether a hit at the floor reads as a comeback chance or a death spiral, and that playtest is the instrument built to answer it, so deciding now is guessing at its result. Do not re-raise before then. The cost that made it a decision rather than an adjustment is a fourth food kind. The reasoning, kept so it is not re-derived: at the floor the grave cannot shrink, so the shrink channel is gone and the score rung carries the entire hit signal on a number nobody is watching. Sonic's rings are a moment of play because they scatter and hand the player a two-second scramble; a number dropping to zero does not. `scoreBled`, `weaponStripped` and `sealed` being separate events is what leaves the door open.

**Dispatch 3b carries a dev route that prints the digest in the browser.** One text node and one function call. ADR 0015's cross-engine claim otherwise goes unchecked until verification step 10 at the end of dispatch 7, because CI and the developer's machine are the same Node, so the digest is a one-engine test for five dispatches. 3b already deploys, so this makes the check "open the URL on a phone and compare one string". Carry it into the 3b plan as a named item, not a nice-to-have.

## Two things to know, needing no action

**`GRAVE_ASPECT` silently sets the Undertaker's difficulty.** His curtain gap is grave width plus a margin, and aspect 2 gives the narrowest width for a given size, so a shallower aspect would mean a wider required gap and an easier boss. Nothing in the plan says so.

**Size-as-health stops working as a health bar above roughly size 40.** A hit at the ceiling moves the half-height 4.4%. Katamari's answer to making scale perceptible is camera zoom against fixed references and ADR 0003 deliberately has no zoom tiers, so the sprite against a fixed field carries it alone. ADR 0014's two-channel rule is the mitigation and it holds, but the other channel is doing the work up there. Consequence for dispatch 4: the hit-taking bot policy has to start from a grown grave, or it measures the three-hit opening and reports on a regime the player spends twenty seconds in.

**`Math.fround` does not shrink a divergence, it changes its shape.** If two engines' f64 results straddle an f32 bucket midpoint, rounding turns a 1-ulp f64 difference into a 1-ulp f32 one, roughly 2^29 times larger. ADR 0015 already states the honest limit so this is not a contradiction, but the Rune citation carries an assumption that does not transfer: Rune's residual divergence is absorbed by server rollback resync and a single-player pinned-seed replay has none. Nothing to do now. Worth writing in ADR 0015 that `math.ts` is where an integer-indexed sine table could later replace the wrappers and make the trig deterministic by construction, so the escape hatch is named before anyone needs it.
